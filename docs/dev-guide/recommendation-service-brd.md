# 推荐服务化商业需求文档（BRD）

回答"为什么做"：招聘商业化的业务痛点、目标、干系人、商业模式与成功指标。承接 [推荐服务化产品设计](./recommendation-service-design.md)，技术实现见 [多租户平台架构设计](./multi-tenant-platform-architecture.md)。

## 背景与业务痛点

### 市场结构

- **市场是企业方市场**：企业方掌握选择权，且生存艰难——理论上不应考虑收企业方的钱，而应把企业方当成**资源**
- **招聘服务市场火热**：海量招聘平台存在，说明客观需求存在；但整个市场**只有流量、缺少信用**——平台与求职者利益天然对立，流量平台补信用极难
- **候选人求职困境**：简历石沉大海、推荐靠人情、没有可携带的能力证明

### 量潮的现状与机会

- 量潮已有：招聘体系（qtrecurit：CLI 采集 + Provider 存储 + Site 招聘门户 + Studio 候选人窗口）、课堂（qtclass：难而贴合企业需求）、人事云（qtcloud-human：招聘/薪资/培训/绩效/关系）
- 量潮积累了大量**历史招聘数据**：真实投递-筛选-结果标注、考核分层、行为记录——市场稀缺的标注资产
- 团队流动性强：持续有一批人被培养成熟并流动——现成的"可推荐资源"
- 痛点：招聘与课堂尚未联动；信用数据（行为记录、评估记录）有积累但未变现；推荐服务无产品形态

## 商业模式（核心决策）

### 决策 1：推荐是服务，不是卖信用

推荐与大部分招聘工具一样：**收服务费，交付服务**（匹配、内推、推荐信、过程反馈），不交付结果担保。推荐不是"把信用卖出去"，而是提供可交付的推荐服务。差异化在于交付物：一般招聘工具卖"流量匹配"（曝光），量潮卖"证据背书"（信用档案）。

### 决策 2：付费与推荐结果隔离

钱买的是"**成为可被推荐的人的过程**"（课堂学习、实训、开源项目参与），不是推荐本身：

- 课堂学费 → 产出真实能力证据的加工过程
- 推荐信 = 凭证据出具的**质检报告**，不是商品
- 付费买不到证据，证据只能靠干活挣——机制上隔离，信任场不因收费而崩

### 决策 3：按交付收费，不按结果收费

- "服务费"对应服务过程（做了内推、出了推荐信、给了反馈），不对应"包你拿到 offer"
- 结果担保是招聘服务被整治的重灾区（付费内推、保 offer、培训贷）——守红线即守信用资产
- 产品结构天然支持：课堂 + 证据 + 服务费，交付物真实存在

### 场域与导流

- 两个场域：**流量场**（课堂）与**信任场**（招聘）。按取舍原则**信任优先**
- 边界划分：**课堂作为导流入口，主体功能做在招聘平台**
- 月度招聘形成范例后被市场充分利用，是**零成本导流**：量潮招聘承接市场流量 → 课堂变现 → 信用复利反哺招聘

## 业务需求

### 对候选人

- BR-1：凭真实行为记录（课堂完成、开源贡献、实训表现）获得可验证的推荐信
- BR-2：付费购买的推荐服务有明确交付物与验收标准（推荐信、内推流程、结果反馈）
- BR-3：付费与推荐结果隔离——付费买过程，不买结果
- BR-4：候选人在量潮积累的信用可携带（投递外部企业时授权披露摘要）

### 对企业（资源方）

- BR-5：免费获得被验证过的人才（信用摘要 + AI 初筛排序）
- BR-6：接入人事云后拥有自己的品牌化招聘前台（`{tenant}.jobs.quanttide.com`）
- BR-7：使用量潮的初步筛选服务（AI 初筛 + 标准模板库），企业 HR 人工复核
- BR-8：企业永远免费——企业是稀缺资源，不赶走

### 对量潮（平台方）

- BR-9：复用量潮历史招聘数据（AI 初筛校准集、初始信用档案、筛选标准模板库）
- BR-10：人事云升级为多租户平台，qtrecurit 作为样板租户（dogfooding）
- BR-11：推荐信为商业化第一个实体交付物——从 mock 到真实数据流
- BR-12：课堂成为导流入口，招聘平台承接流量

## 风险与约束

| 风险 | 应对 |
|------|------|
| 结果担保/付费内推红线（国内整治重灾区） | 按交付收费、不按结果收费；付费与推荐结果隔离 |
| 信任场因收费贬值（"推荐是买来的"） | 付费买过程不买结果；推荐信只凭证据出具，公开可验证 |
| 优秀人才被自己的推荐信送走 | 接受短期流动性，壁垒建在信用复利而非留人 |
| 先有鸡还是先有蛋（无企业资源、无信用数据） | 内部闭环先跑通，再对外讲故事；历史数据迁移解决冷启动 |
| 数据隐私（候选人跨租户数据） | 只共享提炼结果（模型/摘要/模板），不共享原始记录；授权机制 |
| 人事云无后端（当前仅 mock） | 阶段 1 补后端（复用 Provider 模式），多租户骨架先行 |
