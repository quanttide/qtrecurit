# 多租户平台架构设计（人事云 × 招聘前台）

承接 [推荐服务化产品设计](./recommendation-service-design.md) 的商业模式：接入人事云的企业客户可以像量潮自己一样打通招聘前台，由量潮提供初步筛选服务，并复用量潮历史招聘数据作为平台冷启动资产。

## 背景与目标

- 商业模式要求：企业是资源方（免费）、候选人是资产（信用凭证）、收入来自候选人端
- 人事云（qtcloud-human）从"工具"升级为"多租户平台"：企业客户开通租户 → 拥有自己的品牌化招聘前台 → 使用量潮的筛选服务与信用背书
- qtrecurit 是平台的**样板租户**（dogfooding）：量潮自己的招聘就是平台的第一个租户，不换代码验证平台能力
- 历史招聘数据是平台冷启动的**差异化资产**：AI 初筛校准、初始信用档案、筛选标准模板

## 现状

| 系统 | 现状 | 在本架构中的角色 |
|------|------|----------------|
| qtrecurit CLI（Rust） | 数据采集（邮件拉取、漏斗分析） | 采集管道，兼作历史数据迁移管道 |
| qtrecurit Provider（Go） | `candidate`/`criterion` 模型 + filestore | 平台后端原型，演进为多租户服务 |
| qtrecurit Site（React） | 对外招聘门户（岗位、报名、数据公开） | 样板租户前台，多租户化 |
| qtrecurit Studio（Flutter） | 候选人透明窗口（评估/信任记录/推荐信） | 候选人端 |
| qtcloud-human Studio（Flutter） | HR 工作台（招聘筛选/薪资/培训/绩效/关系）+ mock 数据，**无后端** | 多租户化：企业 HR 只看自己租户 |
| qtcloud-human 招聘模块 | 投递邮件初筛、AI 初筛结果审核、匹配度排序 | 筛选引擎的功能来源 |


## 核心决策

| 决策点 | 选项 | 推荐 | 理由 |
|--------|------|------|------|
| 前台形态 | A. 一套 Site 多租户化 B. 每企业独立部署 | **A** | 独立部署是运维灾难；Site 本身就是样板，多租户化成本最低 |
| 数据隔离 | A. 共享库 + 行级 tenant_id B. schema/库 per tenant | **A** | 客户为中小型实习招聘，行级隔离 + 应用层强制过滤是 SaaS 标准；敏感字段按租户密钥加密 |
| 候选人身份 | A. 平台统一身份（email 唯一）B. 租户内身份 | **A** | 信用跨租户携带的前提，也是商业模式的技术根基 |
| 存储演进 | filestore → PostgreSQL | 分阶段 | 初期 filestore 按租户目录（`data/{tenant}/`），数据量上来后迁 PostgreSQL，行级隔离语义不变 |
| 域名与证书 | `{tenant}.jobs.quanttide.com` | 通配符 `*.quanttide.com` | acme.sh 通配符证书实践已有，直接复用 |
| 租户上下文 | 域名 → X-Tenant-ID / JWT claim | 全链路强制 | 前台、筛选引擎、档案服务、工作台统一按租户过滤 |

## 关键机制

### 1. 租户上下文贯穿全链路

前台域名解析租户 → 请求携带 `X-Tenant-ID`（或 JWT claim）→ 筛选引擎、档案服务、HR 工作台全部按租户过滤。量潮自己 = 租户一：qtrecurit 的 Site/Studio 不换代码即变为"旗舰租户"，同时验证平台正确性。

### 2. 筛选引擎 = 共享服务，标准 = 租户配置

qtrecurit Provider 的 `criterion` 模型提升为平台服务：

```
投递 → 租户收件箱 → AI 初筛：
  租户配置的筛选标准（岗位要求、硬性条件）
  + 正文/自荐检测（qtcloud-human 招聘模块已有）
  + AI 匹配度打分（历史标注数据校准）
  → 自动通过 / 自动拒绝 / 需人工复核
  → 企业 HR 在人事云工作台人工复核（AI 初筛结果审核已有）
```

### 3. 信用背书 = 平台级可选能力（差异化落点）

企业"像我们自己一样打通"的最大价值是获得量潮的信用背书：

- 候选人在量潮的信用档案存于 **platform 租户**（不属任何企业租户）
- 企业租户可**开启**"信用背书"开关；候选人投递时**主动授权**
- 前台展示最小化摘要（信用等级/背书状态），不展示原始记录
- 数据边界守住，商业层隔离（见 [推荐服务化产品设计](./recommendation-service-design.md) 三端角色）

### 4. 历史数据复用（平台冷启动资产）

量潮历史招聘数据在三个位置被复用，分别解决不同问题：

**① AI 初筛的校准集**——解决"我们凭什么帮你筛"

量潮历史数据是**真实标注数据**：每封投递邮件 → 筛选结果（通过/拒绝/需复核）→ 录用与否 → 入职后表现。这是多数招聘 SaaS 没有的资产（它们冷启动只有规则，没有标注）。

```
历史标注数据（qtrecurit CLI 采集的真实投递-筛选-结果对）
        │
        ▼
平台级初筛模型（历史数据校准的通用模型）
        │
        ├─→ 新租户冷启动：直接可用（零数据也有初筛能力）
        └─→ 租户数据积累后：租户级微调（岗位特点、企业偏好）
```

**② 信用档案的初始化**——解决"背书凭什么可信"

历史评估记录（考核分层、行为记录、绩效）构成候选人在 platform 租户的**初始信用档案**：推荐信/背书的依据从第一天就有，不用等新数据积累。

**③ 筛选标准的模板库**——解决"新租户配置从哪来"

量潮验证过的筛选准则（考核分层、序列轨道、问卷设计）沉淀为**平台内置模板**，新企业开通时一键启用再按需调整——把"帮忙初步筛选"从定制服务变成产品能力。

```
qtrecurit 存量数据（Provider filestore：投递/评估/漏斗/标准）
        │  ① 一次性迁移（对齐 Provider 模型 → platform 租户）
        ▼
┌─ platform 租户（量潮自己的数据域）────────────────┐
│  候选人档案（含历史评估 → 初始信用档案）           │
│  筛选标准（→ 平台模板库）                        │
│  标注数据（→ 校准初筛模型）                      │
└────────────────────────────────────────────────┘
        │  ② 运行时只读复用
        ▼
   AI 初筛（校准过）· 信用摘要（授权后）· 标准模板（一键启用）
```

**迁移是"对齐"不是"搬运"**：`candidate`/`criterion` 模型即平台模型雏形，迁移时把 filestore 按 platform 租户语义灌入新库，写一次性迁移脚本（CLI 采集管道复用为迁移管道）。存量数据变为租户一的初始状态——**量潮自己就是第一个验证"复用历史数据"的租户**。

**标注数据的价值在于闭环**：历史数据的校准力来自"投递→筛选→结果→入职后表现"的完整闭环。qtcloud-human 的绩效/薪酬/关系模块（记录真实员工表现）正好补上最后一环——历史数据复用是把 qtrecurit（招聘端）+ qtcloud-human（用工端）拼成完整标注链，这是初筛模型的真正护城河。

### 5. 数据边界（复用 ≠ 直接给企业看）

- 初筛排序、信用摘要可以基于历史数据**生成**
- 原始投递/评估记录属于候选人隐私，**不共享**
- 复用的是**提炼后的能力**（模型校准、信用摘要、标准模板），不是原始数据本身
- 授权机制照旧：候选人投递企业 B 时主动授权，企业 B 只看到摘要

## 与现有系统对齐

- **qtrecurit = 样板租户 + 信任场**：CLI 采集写入 platform 租户；Site/Studio 作为租户一的前台与候选人窗口
- **qtcloud-human = 多租户平台引擎**：先补后端（复用 Provider 模式：模型 + 存储 + API），Studio 多租户化（HR 登录 → 只看自己租户）
- **前台域名分离**：量潮自己的 `recurit.quanttide.com` 不动；企业前台挂 `*.jobs.quanttide.com`
- **筛选标准模型**：qtrecurit `criterion` → 平台级模板库 + 租户级配置

## 分阶段演进

| 阶段 | 内容 | 交付物 |
|------|------|--------|
| 阶段 1：多租户骨架 | qtcloud-human 补后端；租户模型 + 行级隔离 + 筛选引擎服务化；qtrecurit 接入成为租户一；历史数据迁移 | 平台后端可用，样板租户跑通 |
| 阶段 2：租户前台 | Site 多租户化（域名路由 + 品牌配置：logo/主题色/slogan）；标准模板库；第一个企业客户开通 | 企业客户上线 |
| 阶段 3：信用背书 | 平台信用服务开放（开关 + 授权 + 摘要）；推荐服务产品化上线 | 商业化闭环 |

## 待拍板问题

1. **"帮忙初步筛选"的深度**：只做 AI 初筛（简历过滤 + 排序，企业 HR 自己面），还是含人工筛选服务（量潮的人帮忙筛）？前者是纯技术架构问题，后者涉及人力运营模式
2. **信用背书开放范围**：默认开放给所有租户，还是只给合作企业？影响平台表设计与授权流程
3. **候选人跨租户数据粒度**：候选人在企业 A 的投递/评估记录，企业 B 能否看到（哪怕匿名）？决定"候选人画像"的共享粒度
